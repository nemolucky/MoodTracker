# Mood Tracker — дневник настроения

## Назначение

Mood Tracker — приложение для ведения дневника настроения и отслеживания эмоционального состояния.
Консольная версия приложения (ПР3) дополнена веб-интерфейсом на Django (ПР5–ПР6) и слоем реляционного хранения данных SQLite с набором SQL-запросов (ПР7).

Приложение позволяет:
* просматривать записи настроения в браузере, получаемые из базы данных SQLite;
* просматривать детальную информацию о конкретной записи со связанными пользователем, настроением и факторами;
* находить записи настроения на выбранную дату с отображением типов настроения, не зафиксированных в этот день;
* просматривать сводную статистику записей и распределение оценок по настроениям (COUNT, AVG, GROUP BY);
* просматривать справочник типов настроения и связанные с ними записи;
* отслеживать динамику и статус настроения по шкале 0-10;
* хранить данные в реляционной базе данных SQLite с обеспечением целостности по внешним ключам;
* переносить существующие данные из JSON-файлов в таблицы базы данных.

## Используемые технологии

* Python 3;
* Django 5.2 — веб-фреймворк;
* SQLite 3 — реляционная СУБД;
* SQL — язык структурированных запросов (DDL, DML, выборки, фильтрация, соединения, агрегация, группировка);
* HTML — разметка веб-страниц;
* CSS и Bootstrap 5.3 — оформление страниц;
* pytest — автоматизированные тесты;
* flake8 — проверка качества кода.

## Целевая аудитория

Люди, которые хотят отслеживать своё эмоциональное состояние и видеть динамику настроения со временем.

## Предметная область

Основными объектами предметной области являются:
* пользователь (`User`);
* запись о настроении (`MoodEntry`);
* тип настроения (`Mood`);
* фактор влияния (`Factor`).

Пользователь создаёт записи о своём настроении за определённую дату, указывая оценку от 0 до 10, комментарий, тип настроения и сопутствующие факторы влияния.

## Основные сущности

### User — пользователь
Объект `User` представляет пользователя системы.
* `id` — уникальный идентификатор пользователя;
* `name` — имя пользователя;
* `email` — адрес электронной почты (необязательный).

### MoodEntry — запись настроения
Объект `MoodEntry` представляет запись о настроении пользователя.
* `id` — уникальный идентификатор записи;
* `entry_date` — дата записи (формат `YYYY-MM-DD`);
* `score` — оценка настроения (0-10);
* `comment` — комментарий пользователя;
* `user` — объект `User`;
* `mood` — объект `Mood` (необязательный);
* `factors` — список объектов `Factor`.

### Mood — тип настроения
Объект `Mood` представляет категорию эмоционального состояния.
* `id` — идентификатор настроения;
* `name` — название настроения;
* `description` — описание настроения.

### Factor — фактор влияния
Объект `Factor` представляет фактор окружения, влияющий на настроение.
* `id` — идентификатор фактора;
* `name` — название фактора;
* `category` — категория (Здоровье, Карьера, Социум, Окружение).

## Реляционная база данных и SQL (ПР7)

В рамках ПР7 в проект добавлен реляционный слой данных на основе SQLite.

### 1. Структура базы данных и таблицы

Файл базы данных: `data/moodtracker.sqlite`.

| Таблица | Поле | Тип | Назначение и ограничения |
| :--- | :--- | :--- | :--- |
| **users** | `id` | INTEGER | Первичный ключ (PRIMARY KEY) |
| | `name` | TEXT | Имя пользователя (NOT NULL) |
| | `email` | TEXT | Электронная почта |
| **moods** | `id` | INTEGER | Первичный ключ (PRIMARY KEY) |
| | `name` | TEXT | Название настроения (NOT NULL) |
| | `description` | TEXT | Описание типа настроения |
| **factors** | `id` | INTEGER | Первичный ключ (PRIMARY KEY) |
| | `name` | TEXT | Название фактора (NOT NULL) |
| | `category` | TEXT | Категория фактора (NOT NULL) |
| **entries** | `id` | INTEGER | Первичный ключ (PRIMARY KEY) |
| | `user_id` | INTEGER | Внешний ключ -> `users(id)` (NOT NULL) |
| | `mood_id` | INTEGER | Внешний ключ -> `moods(id)` |
| | `entry_date` | TEXT | Дата записи (YYYY-MM-DD, NOT NULL) |
| | `score` | INTEGER | Оценка настроения (0-10, NOT NULL) |
| | `comment` | TEXT | Комментарий пользователя |
| **entry_factors** | `entry_id` | INTEGER | Внешний ключ -> `entries(id)` ON DELETE CASCADE |
| | `factor_id` | INTEGER | Внешний ключ -> `factors(id)` ON DELETE CASCADE |
| | | | Составной первичный ключ: `PRIMARY KEY (entry_id, factor_id)` |

### 2. Организация файлов БД

* `sql/schema.sql` — DDL-скрипт создания таблиц с первичными и внешними ключами;
* `sql/queries.sql` — коллекция проверенных SQL-запросов предметной области (12 запросов);
* `db/database.py` — модуль подключения к SQLite (`get_connection()`) с автоматическим включением проверки внешних ключей (`PRAGMA foreign_keys = ON`);
* `db/import_json.py` — скрипт миграции данных из JSON-файлов каталога `data/` в таблицы базы данных;
* `data/moodtracker.sqlite` — файл базы данных SQLite.

### 3. Перенос данных из JSON в SQLite

Скрипт `db/import_json.py` читает исходные файлы `users.json`, `moods.json`, `factors.json`, `entries.json` и с помощью параметризованных команд `executemany()` переносит данные в таблицы SQLite в рамках единой транзакции (`commit()` / `rollback()`).

Запуск импорта:
```text
python -m db.import_json
```

### 4. SQL-запросы предметной области (`sql/queries.sql`)

Файл `sql/queries.sql` содержит 12 запросов, сгруппированных по категориям:
1. **Выборка списков (SELECT, ORDER BY):**
   * Запрос 1: список всех типов настроения с сортировкой по названию;
   * Запрос 2: список всех факторов влияния с сортировкой по категории и названию.
2. **Фильтрация (WHERE):**
   * Запрос 3: записи с высокой оценкой настроения (оценка >= 7, хорошие дни);
   * Запрос 4: факторы влияния из категории «Здоровье»;
   * Запрос 5: поиск записей за конкретную дату (`'2026-09-13'`).
3. **Соединение таблиц (JOIN):**
   * Запрос 6: полная информация о записях с объединением таблиц `entries`, `users` и `moods`;
   * Запрос 7: записи настроения со связанными факторами влияния через связующую таблицу `entry_factors`.
4. **Подзапросы (NOT IN):**
   * Запрос 8: типы настроения, не использованные в записях на выбранную дату (подзапрос исключения занятых сущностей).
5. **Агрегатные функции (COUNT, AVG, MIN, MAX):**
   * Запрос 9: общая статистика записей (всего записей, средний, минимальный и максимальный балл);
   * Запрос 10: количество факторов влияния в разрезе категорий.
6. **Группировка и фильтрация групп (GROUP BY, HAVING):**
   * Запрос 11: количество записей и средний балл по каждому типу настроения (`LEFT JOIN` + `GROUP BY`);
   * Запрос 12: популярные типы настроения с количеством записей не менее заданного (`GROUP BY` + `HAVING`).

### 5. Получение результатов SQL-запросов в Django

Представления Django обращаются к SQLite через стандартную библиотеку `sqlite3`:
* Настройка `conn.row_factory = sqlite3.Row` обеспечивает доступ к полям по именам (`entry["user_name"]`, `{{ entry.user_name }}` в шаблоне);
* Все пользовательские параметры (например, дата при поиске или `id` записи) передаются исключительно через параметризованные запросы с символом `?` (защита от SQL-инъекций);
* Результаты запросов передаются в шаблоны через словарь `context` функции `render()`.

## Страницы веб-интерфейса

* `/` — главная страница: описание сервиса, статистика и навигация (view-функция `index()`);
* `/entries/` — список записей настроения, сформированный через SQL JOIN `entries`, `users` и `moods` (view-функция `entries()`);
* `/entries/<int:entry_id>/` — карточка записи с подробной информацией о пользователе, оценке, настроении и списке факторов (view-функция `entry_detail()`);
* `/entries/search/` — поиск записей на выбранную дату с использованием параметризованного SQL-запроса и выводом типов настроения, не зафиксированных в этот день (view-функция `search_by_date()`);
* `/entries/statistics/` — страница статистики с общими показателями (всего записей, средний/мин/макс балл) и распределением записей по типам настроения и категориям факторов (view-функция `statistics()`);
* `/moods/` — список типов настроения из SQLite (view-функция `moods()`);
* `/moods/<int:mood_id>/` — карточка типа настроения и список связанных записей (view-функция `mood_detail()`).

При отсутствии запрашиваемой записи или настроения возвращается ответ со статусом 404. Несуществующие URL обрабатываются кастомной страницей ошибки 404 (`404.html`).

## Django ORM — ПР9 (актуальная версия)

Веб-интерфейс работает с `db.sqlite3` через ORM. SQL-слой выше описывает
сохранённую реализацию ПР7, которая больше не используется представлениями.
Консольная версия и исходные данные сохранены. Авторизация Django и модель
`entries.User` независимы: последняя описывает владельца дневника ПР7.

### Подготовка и запуск

```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py import_pr7
python manage.py runserver
```

`import_pr7` запускается один раз на пустых предметных таблицах. Источник:
`data/moodtracker.sqlite`; можно указать `--source /path/to/database.sqlite`.
Источник открывается только для чтения. Импорт сохраняет первичные ключи,
внешние ключи и пары M2M в одной транзакции; повторный импорт отклоняется.
Исходная база ПР7 остаётся резервной копией. При ошибке исправьте источник
или параметры и повторите импорт: частично перенесённых данных не остаётся.
Миграции управляют новой схемой; `--fake` для старых таблиц не используется.

### Модели и связи

- `entries.User`: id, name (100 символов), email (необязательный).
- `moods.Mood`: id, name, description (необязательное).
- `moods.Factor`: id, name, category.
- `entries.MoodEntry`: id, user, mood, factors, entry_date, score, comment.

Все id — автоматические BigAutoField. Оценка ограничена 0–10 валидаторами
и CHECK в БД. Дата индексирована. Удаление владельца запрещено PROTECT;
удаление настроения сбрасывает mood в NULL; удаление фактора удаляет только
связи M2M. Обратная связь во всех случаях называется `entries`.
`__str__` даёт читаемое представление каждой сущности.

### Пользовательские сценарии

Прежние URL сохранены. `/entries/` принимает `q` (комментарий, имя владельца
или настроение), `date`, `mood`, `min_score`, `sort` и `page`. Сортировки:
пустая — новые записи первыми; `date` — старые первыми; `score` — высокая
оценка первой; `user` — по имени владельца. Порядок стабилен благодаря id.
На странице 3 записи; ссылки сохраняют фильтры через `{% querystring %}`.
Некорректные фильтры отображают ошибки и пустой список. Некорректный номер
страницы обрабатывает `Paginator.get_page`. `/moods/?q=...` ищет по названию.
Поиск по дате исключает использованные настроения; NULL не мешает исключению.
Статистика включает настроения без записей. Отсутствующие карточки дают 404.

### Проверка ПР9

```bash
python manage.py check
python manage.py showmigrations
python manage.py makemigrations --check --dry-run
pytest -v
flake8 . --extend-exclude=venv
```

Тесты используют отдельную временную БД Django; рабочая БД не изменяется.
Проверяются точность переноса полей и M2M, защита от повторного импорта,
CRUD, валидаторы и CHECK, политики удаления, фильтры, поиск, сортировка,
пагинация, сохранение параметров, статистика и отсутствие N+1 в карточке.
Сгенерированные миграции освобождены только от ограничения длины строк E501.
Подробная самопроверка: `docs/PR9_CHECKLIST.md`.
